# GPUMDkit Web Console 改进执行与复审方案

日期：2026-09-22

用途：交接给实现 agent，完成后由原审查 agent 根据 Git 差异、测试证据和浏览器表现复审，并制定下一轮修改方案。

本轮交接文档本身不修改产品代码，不代替实现结果。下述现状来自 README 和源码静态检查，尚未做浏览器视觉验证；执行者必须先复核，不能把待验证的问题直接写成已复现缺陷。

## 1. 目标与范围

将当前可用的 Web Console 改进为围绕“浏览计算目录 → 理解状态 → 执行分析 → 查看结果”的工作台。优先解决信息组织、结果上下文和监控可信度，再扩展分析能力。

保持以下基础：

- Python 标准库后端，原生 HTML/CSS/JS；离线可用，无 CDN、无前端构建步骤，不引入大型框架。
- 保持 README 声明的 Python 兼容范围；不因 UI 修改顺带提高最低版本。
- 保留现有 CLI、绘图脚本参数和输出文件契约，不修改科学算法、默认拟合范围或单位。
- 保留登录、路径检查、执行锁等现有机制，不扩大默认监听范围。
- 不启动 GPUMD、NEP、DFT、训练、MD、调度任务或昂贵分析。接口测试使用隔离夹具和无副作用的轻量命令。
- 先完成阶段 0–3；阶段 4 是后续候选，留给复审后决定，不在本轮顺手全部实现。

开始前读取：仓库 `AGENTS.md`、`skills/gpumdkit-skill/SKILL.md`、其 `references/contributing.md`、本目录 `README.md`。涉及科学输出解释时，再读取相应 NEP/GPUMD/可视化参考。

## 2. 阶段 0：建立可比较的 Git 基线

用户允许执行 agent 先提交当前已有修改，**只 commit，不 push**。本计划不要求编写文档的 agent 立即提交。

### 2.1 核对已有工作

先执行只读检查：

```bash
git status --porcelain=v2
git diff --stat
git diff --cached --stat
git diff -- gpumdkit.sh Scripts/utils/README.md Scripts/utils/completion.sh docs/updates.info
git ls-files --others --exclude-standard
```

交接时观察到以下已有改动，实际执行时重新确认：

- `gpumdkit.sh`
- `Scripts/utils/README.md`
- `Scripts/utils/completion.sh`
- `docs/updates.info`
- 尚未跟踪的 `Scripts/utils/server/`，包括本交接文档。

逐个检查未跟踪文件内容及已有暂存区，防止把无关修改、凭据、日志、测试输出混进提交。不要使用无差别 `git add .`，不要 reset、clean、stash 或覆盖用户文件；同一文件存在无关改动时只暂存相关区块。若无法确认某段改动归属，保留它并说明阻碍，不猜测处理。

### 2.2 创建基线提交

对确认属于现有 server 功能的修改做基本静态检查，再显式暂存相关文件并提交。建议提交信息：

```text
feat(server): checkpoint initial web console
```

记录完整基线 SHA 为 `BASELINE_COMMIT`。本文件可随基线一同提交，并在交接说明注明。若基线已经由用户或其他 agent 提交，核对后直接记录现有 SHA，不制造空提交。

基线提交后再开始实现。后续按可独立审查的阶段提交，每个提交说明行为变化和验证结果。不得 push、amend 用户提交或重写历史。不要因为工作树还有无关修改而强求全仓库干净。

## 3. 阶段 1：重组工作台和视觉层级

主要文件：`web/index.html`、`web/style.css`、`web/app.js`。

### 3.1 布局

建议结构：

```text
顶部：Logo | 当前目录面包屑 | 连接状态 | 刷新与主题
左侧：目录与文件浏览器
主区：概览 | 数据与文件 | 图像
底部可折叠面板：命令输出 | 执行记录 | 命令执行
```

- 把当前只负责滚动定位的图标栏替换为有明确选中状态的视图切换；不要保留外观像导航、实际只是滚动且容易落空的入口。
- 左侧合并目录和文件列表，保留返回上级、文件过滤，增加名称/修改时间/大小排序；目录始终能清楚区分。
- 当前目录始终可见，长路径省略但可查看或复制完整路径。
- 主区切换与目录切换分别管理状态；自动刷新不应把用户拉回概览或改变正在查看的文件。
- 底部面板默认折叠或保持适度高度，用户执行操作时显示对应输出；允许手动收起。
- 无训练、无推荐操作、无图片、空目录分别显示简洁空状态，说明当前检测到什么和可进行的操作，避免主区只剩终端。
- 窄屏用可收起文件浏览器，优先显示主内容；不要仅把全部侧栏内容堆在页面顶部。

### 3.2 视觉规则

- 中性背景、GPUMDkit 蓝色主操作；绿/橙/红表达状态，不给每块内容独立配色。
- 减少背景渐变、毛玻璃、多层卡片、重复阴影和无意义动画。
- 正文约 14px，次要文字通常不小于 12px；路径、命令、数据用等宽字体。
- 标题以易读为主，减少小号全大写和过大字距。
- 统一间距、边框、圆角和按钮高度，沿用 CSS 变量管理浅色/深色主题。
- 去掉没有实际交互功能的终端红黄绿装饰；不能用颜色作为唯一状态提示。
- 保留清晰的键盘焦点，图标按钮提供可访问名称；尊重减少动画的系统偏好。

### 3.3 推荐操作

将“命令字符串 + Run”改为“用途 + 输入 + 输出 + 操作”。例如：

```text
Mean squared displacement
Input: msd.out    Output: msd.png
View command | Generate figure
```

- 说明直接可见，完整命令可查看和复制，继续调用已有白名单 action。
- 输出存在时显示查看结果和重新生成；根据依赖文件与结果的 mtime 标注可能过期，不把时间比较当作科学有效性证明。
- 按用途做轻量分组；不要无条件隐藏大部分操作，常用操作可见，其余可展开。
- 执行成功更新结果卡片，提供显式打开入口，避免自动弹窗打断用户在其他目录中的操作。
- 本轮不添加需要推测科学参数的新 action。

### 3.4 验收

- 在空目录、NEP 夹具目录、包含多个图片的结果目录分别检查浅色和深色。
- 检查约 1440px、1024px、390px 宽度；没有页面级横向溢出，数据表允许自身横向滚动。
- 导航、文件过滤、滚动位置、主题和底部面板不会被自动刷新重置。
- 核心使用路径不依赖 hover；键盘能到达并操作按钮和视图。

## 4. 阶段 2：监控、刷新和异步上下文

这些是功能可靠性工作，不应被 UI 重构掩盖。可先做成独立修复提交，再接入新界面。

### 4.1 状态表达

现有 `training_status()` 根据 `nep.in` 和 `loss.out` 推导进度，前端根据 `finished` 显示 training/training done。

- 明确区分：发现训练记录、近期数据更新、长时间无更新、记录达到目标代数、读取失败。
- 文件更新不能证明进程正在运行，文件停更不能直接宣称训练失败；显示证据时间和对应描述。
- 目标代数来自文件还是兼容默认值要能分辨；缺少明确目标时不要给用户虚假的精确 ETA。
- ETA 用同一目录、同一训练记录段的多个样本平滑；样本不足显示估算中。
- 切目录、代数回退、文件缩小/重建时重置速率样本。
- 对追加多次训练的 loss 数据说明记录范围，不悄悄把旧训练记录当成本轮训练。

### 4.2 大文件支持

当前 `fetchLoss()` 走 `/api/file`，该接口拒绝超过 512 KB 的文件；后端进度扫描还遍历完整 loss 文件。

- 添加有界的 loss 数据读取接口或等价专用路径，不通过提高所有文件预览上限解决。
- 进度从文件尾部寻找最新完整、有效记录；处理末行写入一半的情况。
- 曲线响应有点数上限，采用明确的降采样策略；保留首尾和重要变化，界面标明采样。
- 根据文件变动缓存/增量更新，处理追加、截断、替换；避免每次刷新完整扫描和发送大文件。
- 不改变既有 loss 列含义；横轴按实际提供的数据说明为记录序号或经验证的代数，不能把采样后的位置冒充原始代数。
- 覆盖非数值行、空文件、非有限值、非正值在对数坐标下的行为；给出明确提示，不能静默制造看似正常的曲线。

### 4.3 刷新体验与性能

- 所有文件 mtime 比较采用服务器时间；核对 `renderDirList` 当前传入客户端时间的路径。
- 自动刷新失败显示连接问题与最后成功更新时间，保留旧数据并标识其过期；恢复后清除提示。
- 区分数据采样时间与自动刷新间隔，避免用户把 60s idle check 当作最后更新于 60 秒前。
- 只更新发生变化的列表项、监控值和图片；目前 `renderFigures()` 每次清空重建，应避免无意义重新加载。
- 保持后台标签页降低轮询频率的行为；避免重复定时器和重叠请求堆积。

### 4.4 异步上下文

至少核对并修复以下路径：

- `fetchLoss()` 返回时检查目录/请求序号，旧目录响应不能画到新目录。
- `runAction()` 启动时捕获工作目录；返回结果、图片路径和历史绑定启动目录，不使用返回时的 `curPath`。
- `saveText()` 捕获文件路径与文档版本；保存响应不能把新打开文件的前端状态改成旧文件内容。
- 文件预览成功、错误和异常分支都检查请求归属，关闭预览后失效旧请求。
- 目录切换后清空跨目录的文件增长和训练速率比较基线。

### 4.5 验收

用延迟响应或可控测试模拟：在 A 目录发请求后立即切 B；在保存 A 文件期间打开 B 文件；绘图返回前切目录。结果不能串目录、串文件或误报速率。

用小于和大于 512 KB 的合成 loss 文件、追加中末行、截断/重建文件验证监控。记录测试数据量、响应体点数上限和耗时观察，不声称已经证明所有 HPC 场景下的性能。

## 5. 阶段 3：文件操作与执行结果闭环

### 5.1 文件预览和编辑

- 文件预览优先在主区或可收起侧面板呈现；若保留模态框，补齐焦点进入、Esc、焦点恢复和可访问名称。
- 增加未保存标记；关闭、切文件、切换会丢弃草稿的模式前提醒。保存失败保留草稿。
- Form 与 Edit 的草稿应保持一致，不能切标签后悄悄恢复旧内容。
- 保存请求携带打开时的版本标识，后端检测外部修改并返回冲突；默认不覆盖新内容。冲突提示提供重新读取和保留当前草稿的方式。
- 原子替换仍要保留；版本检查与写入尽可能串行处理，说明无法完全阻止外部进程竞争的边界。
- 大文本提供有界头部/尾部预览及截断提示；截断内容不可作为完整文件直接保存。
- 只给可靠识别的格式加列名/单位，不明格式使用列编号。
- 数值查看支持明确选择 X/Y 列、多条曲线和线性/对数坐标；悬停显示真实样本值。
- 科学输入继续忠实保留顺序、重复关键词、注释和换行，不能为了表单美观改变语义。

### 5.2 执行记录和结果

每条执行记录至少包含：操作名/命令、启动目录、开始时间、耗时、状态、退出码、输出、结果文件路径。

- 查看输出、复制命令、打开结果绑定该记录。
- 明确区分启动失败、退出非零、超时和网络中断；网络中断不能直接断言后端命令已停止。
- UI 同步呈现已有后端执行锁状态，避免用户在推荐操作和终端间反复遇到不解释原因的 busy。
- 本轮记录可先保持会话内有界存储，并明确刷新后是否保留；持久化方案不得默认把可能含敏感信息的任意终端命令长期写入浏览器或服务器。
- 命令输出截断时显示提示；退出成功不代表科学结果有效。

### 5.3 命令执行面板

- 现有实现每次使用独立 `bash -c`，不是持续 shell；面板明确说明不会保留 export 等会话状态。
- 清楚显示执行目录、执行中状态、120 秒限制和返回结果。
- 不在本轮扩展为完整 PTY、不添加训练启动器或调度管理。
- 不提供没有后端保证的“取消”按钮。流式输出、任务 ID、可靠取消作为后续专项设计。
- README 中的路径限制适用于文件 API 和工作目录选择；任意 shell 并非操作系统沙箱。描述实际能力边界，不能将工作目录限制宣称为 shell 文件系统隔离。

### 5.4 验收

- 外部修改文件后再保存，能够报告冲突，原始文件不被无提示覆盖。
- 修改草稿后切换/关闭有保护；成功保存后状态复位，失败后草稿保留。
- 超限预览有解释，不出现空白窗口；不允许保存截断文件覆盖完整文件。
- 不同目录的同名图片、同名输入文件和执行记录准确关联。
- 轻量成功命令、非零退出命令、执行锁冲突以及模拟网络错误均有明确反馈。

## 6. 阶段 4：复审后再安排的扩展

本轮只记录方案，不实现：

1. 多目录训练对比：先解决记录身份、时间范围、曲线采样和比较口径。
2. 温度目录汇总：先展示现有数据完整性，再设计拟合交互；不自动选择拟合窗口或科学参数。
3. 图片并排比较、统一缩放和下载：保证来源目录、生成时间和命令可追溯。
4. 参数化绘图：逐项核实脚本帮助和参数契约，再设计类型化参数表单。
5. 流式输出/后台任务：先定义任务身份、断线重连、输出上限、取消与子进程清理语义。

原审查 agent 根据阶段 1–3 的实际结果重新排序，不默认要求全部添加。

## 7. 实施与文档约束

- 允许按状态和渲染职责拆分原生 JS 文件，但不进行没有实际收益的全量重写；静态资源路由与离线能力同步验证。
- 只修改 server 及必要集成点，避免触碰 `Scripts/plt_scripts/` 的科学逻辑。
- 更新本目录 README，使 API、状态、编辑行为和已知边界与实现一致。
- 用户可见行为涉及教程时，同步相关英文/中文来源；不做无关文档扩写。若修改教程，按贡献约定构建并验证生成文档。
- `docs/updates.info` 只记录实际功能和 bug 修复，不记录本计划、文案或纯文档修改；每类最多五条。
- 修改 `gpumdkit.sh` 才更新其 VERSION 中日期为执行当天日期，保留版本号；未修改入口时不为更新日期触碰它。

## 8. 验证、清理与交付

### 8.1 基本检查

```bash
bash -n gpumdkit.sh
python3 -B -c 'from pathlib import Path; p=Path("Scripts/utils/server/server.py"); compile(p.read_text(), str(p), "exec")'
node --check Scripts/utils/server/web/app.js
git diff --check
```

拆分 JS 后逐个检查新增文件。针对实际修改增加有意义的回归测试，重点是异步竞态、版本冲突、有界大文件读取和状态判断，不用大量镜像实现的测试替代浏览器验证。

### 8.2 隔离测试

- 创建唯一临时目录，记录其绝对路径；在该目录放合成输入并通过文档化入口启动仅监听 loopback 的测试服务。
- 覆盖登录模式、目录扫描、普通/超限文件、图片、保存和轻量执行；不要把真实工作目录当写入夹具。
- 涉及绘图流程时优先使用可控轻量夹具；不启动科学模拟，不因缺依赖安装大型环境。
- 浏览器检查控制台错误、请求失败、深浅主题、响应式布局、键盘操作和自动刷新。
- 保留改前/改后截图作为交付证据，明确夹具数据；正式证据放用户允许的持久目录，报告绝对路径，不误称临时文件已清理却留下截图。
- 如果没有可用浏览器或运行环境，明确标记未验证项，不能声称全部完成。

### 8.3 清理

停止本轮启动的服务，只终止已记录并核对归属的进程。删除本轮创建的临时目录、缓存、测试输出，包括失败命令留下的文件；只删除已核实的精确路径。最后只读检查这些路径与 Git 状态，报告残留情况，不删除用户原有文件。

### 8.4 最终交付内容

执行 agent 的最终回复必须包含：

1. `BASELINE_COMMIT` 完整 SHA，以及每个实现提交的 SHA 和主题。
2. 完成范围，按阶段列出；明确未完成、延期和设计偏离。
3. 关键文件与行为变化；API 变动及兼容性影响。
4. 静态检查、接口测试、浏览器测试分别说明，附命令、结果和视觉证据位置。
5. 已知限制，尤其是训练状态推断、文件竞争、终端会话和大文件采样。
6. 清理结果及剩余工作树变更的归属。
7. 明确声明“已本地提交，未 push”。

## 9. 原审查 agent 的复审流程

用户通知实现完成后，再执行本节；本文件不会自动创建后台监控或调度任务。

1. 读取交付说明，核对基线 SHA、实现提交、当前分支和工作树。记录实际审查 HEAD；若有后续用户改动，单独识别。
2. 用 `git diff BASELINE_COMMIT..REVIEW_HEAD -- Scripts/utils/server` 及相关集成文件审查最终差异；另看未提交差异，不能遗漏或混入历史基线。
3. 先验证结果上下文、保存保护、监控数据正确性，再评估布局和视觉；不以截图好看代替功能正确。
4. 重现关键路径：大 loss 文件、断网恢复、A/B 目录快速切换、外部修改后保存、同名结果文件、窄屏和深色模式。
5. 输出有证据的发现：严重程度、具体触发条件、影响、文件位置、最小修改建议；区分确定缺陷、待运行验证和主观设计建议。
6. 明确本轮可接受与不可接受项，再给出下一轮范围和验收条件。优先修复已发现问题，再从阶段 4 选择收益最高的扩展。
7. 下一轮方案仍围绕可审查的小改动和独立提交；不自动 push，不擅自扩大为科学执行任务。

复审交付应让下一个 agent 能直接行动：每个问题写明改哪里、为什么、如何验证，而不是只说“继续优化 UI”。
